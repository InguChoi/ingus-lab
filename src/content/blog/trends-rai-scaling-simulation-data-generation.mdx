<section data-lang="ko">

RAI Institute가 [Scaling Simulation Data Generation](https://rai-inst.com/resources/blog/scaling-simulation-data-generation/)을 공개했습니다. 부제는 "How AnyTask and ExpertGen Bridge the Sim-to-Real Gap"입니다. 글의 중심은 시뮬레이션을 단순한 synthetic data 공장으로 쓰는 것이 아니라, foundation model을 위한 다양한 로봇 행동 데이터를 자동으로 설계하고 검증하는 시스템으로 확장하려는 시도입니다.

앞선 RAI Koala 글이 실제 환경에서 handheld gripper로 데이터를 모으는 문제를 다뤘다면, 이번 글은 그 반대쪽 축을 다룹니다. 실제 데이터는 물리적으로 믿을 수 있지만 scale이 어렵고, 시뮬레이션은 scale이 쉽지만 physics와 task 설계가 병목입니다. RAI의 메시지는 이 병목을 LLM, VLM, procedural generation, reinforcement learning으로 줄이겠다는 쪽에 가깝습니다.

## 무엇이 나왔나

RAI는 두 가지 내부 파이프라인을 소개합니다. `AnyTask`는 high-level task description과 object database에서 출발해 구체적인 task description, scene, success checker, reset function, state observation, scripted policy, dense reward code를 생성하는 시뮬레이션 데이터 생성 파이프라인입니다.

`ExpertGen`은 AnyTask 같은 시스템이 만든 scripted trajectory만으로는 풀기 어려운 contact-rich 행동을 보완합니다. Demonstration trajectory로 diffusion policy prior를 학습한 뒤, massively parallel reinforcement learning으로 성공적인 behavior를 찾습니다. 이때 dense reward engineering에 강하게 의존하기보다 sparse success checker를 사용한다는 점이 중요합니다.

핵심 변화는 "시뮬레이션에서 데이터를 많이 만든다"가 아닙니다. task 설계, scene 구성, reward와 success 판단, behavior generation, visual policy distillation까지 데이터 생성 과정의 여러 병목을 자동화하려는 점입니다.

## 왜 중요한가

로봇 foundation model에 필요한 데이터는 단순히 trajectory 개수가 많다고 해결되지 않습니다. 데이터는 robot embodiment와 맞아야 하고, task가 다양해야 하며, force와 contact가 포함된 행동을 충분히 담아야 합니다. Teleoperation은 target robot과 embodiment gap이 작지만, operator가 distant workspace에 자신의 행동을 옮겨야 하고 force feedback이 약한 경우가 많습니다. Handheld device는 더 자연스러운 demonstration과 야외 데이터 수집이 가능하지만, robot joint angle 같은 robot-internal observation을 직접 얻기는 어렵습니다.

시뮬레이션은 이 빈 공간을 채울 수 있습니다. robot embodiment, joint state, privileged state, 빠른 반복 실행, super-human policy search를 모두 다룰 수 있기 때문입니다. 하지만 asset이 단순하거나 contact model이 현실과 다르면 sim-to-real gap이 남습니다. Domain randomization도 결국 friction, restitution, lighting, camera, background 같은 분포를 어느 정도 잘 잡아야 효과가 있습니다.

그래서 이번 글의 신호는 simulation scale 자체보다 simulation authoring scale에 있습니다. 로봇 팀이 매 task마다 환경, reward, success condition, scene distribution을 손으로 만드는 구조라면 foundation model급 task diversity에 도달하기 어렵습니다.

## 기술적 신호

AnyTask에서 눈에 띄는 부분은 task를 language-level description에서 code-level simulation object로 내리는 과정입니다. 예를 들어 "stacking" 같은 추상적 목표와 object database가 있으면, LLM이 더 구체적인 task들을 만들고 각 task에 필요한 code fragment를 생성합니다. 성공 판정, reset, observation, scripted policy, reward가 모두 데이터 생성 단위가 됩니다.

또 하나의 축은 semantically meaningful scene generation입니다. "drawer에서 물체를 꺼내기"를 학습하려면 물체가 실제로 drawer 안에 있어야 합니다. RAI는 object-wise spatial relationship과 batched GPU-accelerated collision checking을 이용해 이런 장면을 빠르게 생성한다고 설명합니다. 원문은 이 방식이 기존 방법보다 200배 빠르게 관계를 만족하는 scene을 만들 수 있다고 말합니다.

하지만 LLM이 만든 code가 항상 맞지는 않습니다. 좌표계 변환, 물체 기하, kinematics, dynamics를 잘못 가정할 수 있습니다. 그래서 RAI는 VLM이 text description과 image observation을 검사하고, success checker, scripted policy, reward alignment를 반복적으로 고치는 refinement loop를 둡니다. 이 구조는 "LLM이 코드를 한 번 생성한다"보다 "시뮬레이션 실행 결과를 보며 고친다"에 가깝습니다.

ExpertGen은 behavior generation의 다른 병목을 겨냥합니다. LLM-generated reward로 학습한 RL policy는 simulator나 reward의 빈틈을 exploit할 수 있고, scripted policy는 현실적인 semantic prior를 지키기 쉽지만 irregular object pushing 같은 reactive contact task에서는 약해질 수 있습니다. ExpertGen은 diffusion policy prior와 RL search를 결합해, demonstration distribution 안에 머물면서 성공하는 행동을 찾으려 합니다.

마지막 단계도 중요합니다. ExpertGen으로 만든 state-based expert는 simulation의 정확한 object pose 같은 privileged state를 쓸 수 있지만, 실제 로봇은 그런 정보를 그대로 갖지 못합니다. RAI는 DAgger를 사용해 이 expert를 visual policy로 distill하고, background, camera parameter, lighting condition을 randomize해 zero-shot RGB sim-to-real을 노립니다.

## 시장 또는 제품 관점

이 글은 제품 발표라기보다 로봇 데이터 인프라의 방향을 보여주는 연구 노트에 가깝습니다. 최근 physical AI 흐름에서 "더 많은 데이터"는 반복되는 구호지만, 로봇에서는 데이터 생산 자체가 비쌉니다. RAI의 접근은 사람의 demonstration, handheld data collection, simulation generation, on-robot refinement를 서로 대체재가 아니라 보완재로 놓습니다.

제품 관점에서 보면 중요한 경쟁력은 simulator 하나가 아니라 data generation loop 전체입니다. task를 만들고, scene을 만들고, success를 판단하고, behavior를 생성하고, visual policy로 옮기고, 실제 로봇에서 실패를 다시 보정하는 반복이 짧아질수록 새로운 skill을 추가하는 비용이 낮아집니다.

다만 아직 남는 질문도 분명합니다. AnyTask가 생성한 task와 ExpertGen이 만든 policy가 어느 범위의 object, contact, deformable material, long-horizon task까지 버티는지는 더 봐야 합니다. 또한 sim-to-real은 zero-shot 성능만으로 끝나기 어렵고, RAI도 future work에서 real-world data와 on-robot refinement를 함께 쓰는 방향을 언급합니다.

<section data-lang="en">

RAI Institute has published [Scaling Simulation Data Generation](https://rai-inst.com/resources/blog/scaling-simulation-data-generation/), with the subtitle "How AnyTask and ExpertGen Bridge the Sim-to-Real Gap." The post is not just about using simulation as a synthetic data factory. It is about scaling simulation into a system that can design, generate, and validate diverse robot behaviors for foundation models.

If RAI's earlier Koala post focused on collecting real-world manipulation data through handheld grippers, this post covers the other side of the stack. Real data is physically grounded but hard to scale. Simulation scales well, but physics fidelity and task authoring become bottlenecks. RAI's direction is to reduce those bottlenecks with LLMs, VLMs, procedural generation, and reinforcement learning.

## What Changed

RAI introduces two internal pipelines. `AnyTask` starts from a high-level task description and an object database, then generates concrete task descriptions, scenes, success checkers, reset functions, state observations, scripted policies, and dense reward code for simulation data generation.

`ExpertGen` addresses the contact-rich behaviors that are hard to solve with scripted trajectories alone. It fits a diffusion policy prior from demonstration trajectories, then uses massively parallel reinforcement learning to search for successful behavior. The important detail is that it leans on a sparse success checker instead of relying heavily on dense reward engineering.

The shift is not simply "generate more data in simulation." It is an attempt to automate several bottlenecks at once: task design, scene construction, reward and success definition, behavior generation, and visual policy distillation.

## Why It Matters

Robot foundation models do not become useful just because the trajectory count goes up. The data has to match the robot embodiment, cover diverse tasks, and include enough force and contact behavior. Teleoperation has a small embodiment gap because the target robot itself is being controlled, but the operator often has to map their actions into a distant workspace and may have limited force feedback. Handheld devices can produce more natural demonstrations and collect data outside the lab, but they do not directly provide robot-internal observations such as joint angles.

Simulation can fill part of that space. It can match a chosen robot embodiment, expose joint state and privileged state, run quickly, and support super-human policy search. But if assets are simplified or contact models are off, the sim-to-real gap remains. Domain randomization helps only when distributions such as friction, restitution, lighting, cameras, and backgrounds are reasonable enough.

The signal in this post is therefore not only simulation scale. It is simulation authoring scale. If each task still requires engineers to hand-build environments, rewards, success conditions, and scene distributions, it is hard to reach the task diversity expected from foundation-model-scale robotics.

## Technical Signals

The key move in AnyTask is turning a language-level task description into code-level simulation objects. Given an abstract goal such as stacking and a database of objects, an LLM can propose more concrete tasks and generate the code fragments needed to instantiate them. Success checking, reset logic, observation construction, scripted policies, and rewards all become part of the data generation unit.

Another axis is semantically meaningful scene generation. To learn "take an object out of a drawer," the object needs to start inside the drawer. RAI describes a framework that uses object-wise spatial relationships and batched GPU-accelerated collision checking to generate such scenes efficiently. The post says this can generate relationship-satisfying scenes 200 times faster than existing methods.

LLM-generated code is not always correct, though. It can make wrong assumptions about coordinate frames, geometry, kinematics, or dynamics. RAI therefore adds a refinement loop in which a VLM inspects text descriptions and image observations from policy execution, then helps check whether the success checker, scripted policy, and reward are aligned with the desired behavior. This is closer to "generate, run, inspect, and repair" than to one-shot code generation.

ExpertGen targets a different bottleneck in behavior generation. RL policies trained with LLM-generated rewards can exploit weaknesses in the simulator or reward function. Scripted policies are often better at preserving semantic priors and realistic motion, but they can fail on reactive contact tasks such as pushing an irregular object across a table. ExpertGen combines a diffusion policy prior with RL search, trying to find successful behavior while staying within the demonstration distribution.

The final step matters too. State-based experts created in simulation can use privileged information such as accurate object poses, but real robots do not usually have those signals directly. RAI uses DAgger to distill these experts into visual policies, while randomizing backgrounds, camera parameters, and lighting conditions to target zero-shot RGB sim-to-real transfer.

## Market or Product View

This reads less like a product launch and more like a research note about robot data infrastructure. In physical AI, "more data" is a common refrain, but in robotics the production of data is itself expensive. RAI's framing treats human demonstrations, handheld data collection, simulation generation, and on-robot refinement as complementary sources rather than substitutes.

From a product perspective, the key capability is not only the simulator. It is the entire data generation loop. The faster a team can create tasks, generate scenes, judge success, produce behavior, distill visual policies, and refine failures on real robots, the lower the cost of adding new skills becomes.

Open questions remain. We still need to see how far AnyTask-generated tasks and ExpertGen policies hold up across object categories, contact regimes, deformable materials, and long-horizon tasks. Sim-to-real is also unlikely to end at zero-shot transfer alone. RAI points toward future work that combines simulated data generation with real-world data and on-robot refinement.

## Ingus Lab Comment

The interesting part of this post is that simulation is treated less as a fake copy of the world and more as a programmable testbed for producing behavior data. For robot foundation models, the bottleneck is not only model architecture. It is also how quickly teams can create, test, and discard diverse tasks.

I also think the connection between AnyTask and Koala is important. If simulation can rapidly create tasks and privileged experts, while handheld devices and on-robot refinement correct real contact behavior, the robot data flywheel starts to look more practical.
